# Diff presentation findings

- `GET /api/runs/:id` is declared in `apps/api/src/api.controller.ts:163-166`. Its service response selects artifact summaries as `{ id, kind, contentHash, createdAt }` and returns them under `artifacts` (`apps/api/src/api.service.ts:269-300`). The web type must still treat that collection defensively because `apiGet<T>` does not validate the response.
- `GET /api/runs/:id/artifacts/:artifactId` is declared in `apps/api/src/api.controller.ts:168-175`. The service returns the persisted artifact row, including `content`, or a 404 (`apps/api/src/api.service.ts:303-310`). The database shape is in `packages/db/src/schema.ts:250-265`.
- The canonical artifact kind is `diff` (`packages/domain/src/enums.ts:130-145`). Both MVP coding and team integration persist diff content as `{ diff, baseBranch, branch }` (`apps/worker/src/mvp-stages.ts:324-331`, `apps/worker/src/team-stages.ts:329-336`). Base branch and working branch are therefore confirmed present for newly produced diff artifacts.
- Diff artifacts do not persist task, stage, or iteration attribution. Those fields are modelled as optional and rendered only when a future or older producer actually supplies them. The adjacent integration report has `iteration`, but that is a different artifact and must not be projected onto the diff (`apps/worker/src/team-stages.ts:317-327`).
- Artifact content may be `null` when `storageRef` is populated. The current API service returns the row without resolving object storage, so the web UI treats unavailable content as an error rather than an empty diff.
